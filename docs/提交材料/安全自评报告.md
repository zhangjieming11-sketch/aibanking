## 一、自评结论（TL;DR）

本作品的核心命题是：**智能体永远只是「申请人」，永远不是「执行人」**。所有写操作（尤其是资金操作）必须回到用户本人的两道凭证，且安全决策不经大模型。我们围绕这一命题构建了五道纵深防线，并对已知风险做了**主动、如实披露**——我们认为，承认边界比声称无懈可击更可信。

| 维度 | 自评结果 |
|---|---|
| 权限分级 | 30 个动作硬编码 P0–P3，高危 5 项永久无权，安全决策不经 LLM |
| 参数完整性 | HMAC-SHA256 参数指纹，改一个字符即失效 |
| 双因子验证 | P2 资金操作强制支付密码 + 短信验证码，共用失败计数 3 次锁单 |
| 数据隔离 | 注入防火墙 70/70 拦截 + 25/25 无误伤 |
| 审计不可篡改 | HMAC 审计哈希链 + 启动自检 + 现场校验 |
| 已知风险 | 已识别 30+ 项，逐项标注状态（已修复 / 部分 / 未修复 / 设计取舍） |

## 二、权限分级实现说明

权限分级是本系统安全的「第一性原理」：每个 API 动作都被硬编码一个权限级别，**安全决策不经 LLM**，LLM 的输出只作为不可信的「意图提议」。

### 2.1 分级模型

实现位置：`lib/gateway.js` 的 `POLICY` 表（共 **30 个动作**）。

| 级别 | 含义 | 智能体可执行性 | 确认要求 |
|---|---|---|---|
| **P0 只读** | 查余额 / 查账单 / 查持仓 / 查产品 / 扫订阅 / 读记忆 | 直接回答 | 登录态即可 |
| **P1 低敏写** | 定时转账、取消订阅、AA 发起、写记忆、计划创建/调整/回滚、绑卡、冻结/解冻、设默认卡 | 申请 + 一次确认 | 一次性授权单 |
| **P2 资金** | 转账、挂失、锁资、AA 付款、理财申购、理财赎回 | 申请 + **支付密码 + 短信验证码** | 双因子授权单 |
| **P3 高危不可逆** | 解绑卡、修改支付密码、重置支付密码、解绑手机、关闭安全策略（**5 项**） | **Agent 永久无权，仅本人 App 内凭支付密码操作** | — |

**关键设计**：P3 不是「暂不支持」，而是产品结论。把解绑卡、改支付密码这类最高危权限交给一条可能被注入的链路，等于把最高危权限外包给模型。对 `actor === 'agent'` 命中 P3，网关在权限层直接拦截，不看 LLM 说什么。

### 2.2 拦截分层（用户可见的「被谁拦的」）

`lib/gateway.js` 定义 4 个拦截层，每一条拦截卡都标注来源，便于审计与申诉：

- `DATA` 数据隔离层 —— 不可信数据进入指令层前被拦（`lib/injection.js`）
- `RESOLVE` 收款人解析层 —— 代称无法落到已验证联系人（`lib/contacts.js`）
- `POLICY` 权限层 —— 动作超出 P 级策略，Agent 永久无权
- `VERIFY` 校验层 —— 授权单签名 / 时效 / 凭证校验不通过

### 2.3 授权单与一次性确认（P2 资金操作核心）

P2 动作不走「调用即执行」，而是 **建单 → 用户双因子确认 → 执行 → 用后即废**：

1. **建单**：`gateway.createApproval` 校验动作白名单、参数 schema、收款人闸门（转账必须有 `contactId`）后生成授权单；`fillResourceDefaults` 把卡/持仓 ID 回填进指纹，使资源 ID 也受 HMAC 保护。
2. **参数签名**：`signParams`（HMAC-SHA256，密钥 `SIGN_KEY` 仅服务端）将 金额/收款人/收款账户/资源ID 一并签入，派生人眼可核对指纹（如 `0FC5·646A`）。
3. **用户确认**：`confirmAndExecute` 在互斥锁临界区内执行，依次校验 ①签名 ②参数比对（防前端篡改金额）③支付密码（scrypt + `timingSafeEqual`）④短信验证码；失败共用计数 3 次即 `status='locked'` 整单作废。
4. **幂等与时效**：授权单 5 分钟有效（`APPROVAL_TTL`），用后 `status='used'`；以单 ID 作幂等键，重复提交只执行一次。
5. **并发安全**：确认由 `lock.mutex` 互斥 + 幂等键保证并发重复确认只扣一次资金（竞态测试资金净变动 ¥0.00）。

### 2.4 双因子与限速

- **P2 双因子**：支付密码 + 短信验证码共用失败计数，3 次锁单（`MAX_ATTEMPTS=3`）。
- **用户级累计限速**（防「换单刷次数」）：支付凭证失败 10 分钟 5 次冻结 15 分钟。
- **登录限速**：5 次错误密码锁 5 分钟 + IP 15 次（实测第 6 次返回 429）。

### 2.5 审计哈希链

每条审计记录存 `prev_hash` 与上一条 `hash`，形成 HMAC 链；`verifyAuditChain()` 逐条重算并校验衔接，篡改任意一条即断链。日志超 2000 条触发分级保留（关键事件全留、常规留最近 800）并 `resealChain()` 重封，避免裁剪后误报断链。前端顶栏常驻「🔗 审计链完好·N」徽标，可一键现场校验。

## 三、五道安全防线（纵深防御）

| 防线 | 实现位置 | 机制 |
|---|---|---|
| **① 数据隔离层** | `lib/injection.js` | 唯一注入判定入口，正则覆盖指令覆盖、角色劫持、权限提升、绕过验证、系统提示套取、数据渗漏等 8 类；NFKC 归一化 + 去零宽字符；业务咨询（风控/规则）豁免，避免误伤。外部数据入库前逐行清洗。 |
| **② 权限分级** | `lib/gateway.js` POLICY | P0–P3 硬编码，白名单外一律拒绝，P3 对 Agent 永久拦截。 |
| **③ HMAC 参数指纹** | `lib/util.js` | 金额/收款人/账户/资源ID 签入 HMAC，恒定时间比对防时序侧信道；改任一字符即失效。 |
| **④ 可信收款人解析** | `lib/contacts.js` | 三态信任：verified（正常）/ pending（单笔≤¥50，红字警示）/ unknown（拒绝+引导，绝不猜测）；同音识别用同音字表强信号；归一化去零宽/全角/分隔符。 |
| **⑤ 审计哈希链** | `lib/gateway.js` | prev_hash + hash 串链，篡改即断链，可现场校验。 |

**通道隔离补充（最新）**：转账存在两条物理隔离的入口——对话助手通道走可信通讯录（Agent 无权把不在通讯录的卡号变收款人），而「卡号直转」通道**仅由用户本人在表单手填姓名+卡号触发**，切断「提示词注入伪造收款卡号」路径；忘记/重置支付密码的人脸+短信双因子同样属于「仅本人可触达」的 P3 独立通道。

### 4.4 架构性已知限制（设计取舍，非缺陷）

1. **黑名单/注入为规则匹配非智能识别**：谐音、拼音、强对抗改写存在边界。
2. **演示短信为模拟发送**：验证码自动展开在面板，非真实下发。
3. **限速为进程内内存计数**：重启清空，生产需换 Redis。
4. **进程内互斥锁只防单实例**：多实例需下沉 DB 行锁。
5. **A1.8 复合意图（"转账+通知对方"）未实现**。
6. **会话历史不落库**：刷新后仅草稿恢复，非完整对话续接。
7. **无障碍与适老化未做**：M1–M5 假设用户能读卡片、能打字。
8. **单文件 JSON 存储**：演示可 reset，非生产级事务存储。

## 六、安全设计理念小结

1. **不假设模型是对的**：模型输出只是意图提议，必须过网关、过校验、过用户确认。
2. **把权限做成结构**：P0–P3 硬编码，高危动作永久无权，安全决策不经 LLM。
3. **把确认做成数学**：HMAC 指纹改不了，不是「约定不要改」。
4. **把攻击做成回归**：70 条攻击 + 25 条误伤对照，每次合并必须全绿。
5. **通道隔离**：Agent 通道与本人手填通道物理隔离，切断「注入伪造收款卡号/高危操作」路径。
6. **诚实披露**：已知风险逐项标注状态，主动承认边界。

> 安全架构是可移植的——P0–P3、HMAC 指纹、审计链、数据隔离这四件，换任何存储/任何模型都成立。
