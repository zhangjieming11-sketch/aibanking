## 一、一句话定位

**我们做的不是会聊天的银行 App，而是一套让智能体可以安全地替你办成事的架构。**

具体到工程上是一句话：**智能体永远只是「申请人」，永远不是「执行人」。**
它能理解、能规划、能组合工具、能跨场景编排，但它产生的每一个写操作，都必须回到用户本人的两道凭证上。

---

## 二、核心命题与破题思路

### 2.1 真正的问题在哪里

行业里做「AI 银行」，通常把难点理解为「模型够不够聪明」。但在真实业务里，难点是另外三个：

| 真实难点 | 表现 | 只靠模型能不能解决 |
|---|---|---|
| 模型会理解错 | 用户说「转给他」，指代错人；说「给妈妈转」，同音字选错 | 不能，需要结构化的可信数据源 |
| 模型会被骗 | 账单商户名里藏指令、上传文件里藏指令 | 不能，需要通道隔离 |
| 模型会幻觉 | 「上个月」被解析成 2023-09 | 不能，需要服务端时间作为唯一真相 |

所以我们的设计前提是：**不假设模型是对的**。模型输出只是一个「意图提议」，必须过网关、过校验、过用户确认。

### 2.2 三层解法

```
第一层：把权限做成结构   →  P0–P3 分级，高危动作智能体永久无权
第二层：把确认做成数学   →  HMAC 参数指纹，改一个字符就失效
第三层：把攻击做成回归   →  70 条攻击用例 + 25 条误伤对照，每次合并必须全绿
```

### 3.1 为什么坚持零依赖

答辩现场可能没有网络。`npm install` 失败一次，演示就没了。零依赖意味着**只要有 Node，就能跑起来**；模型不可用时还能降级到规则引擎（E5 已实测）。

## 四、五道防线（逐层说明为什么这么设计）

### 防线一：数据隔离层 —— 数据可以被读懂，但不能变成指令

`lib/injection.js`

不可信数据（用户输入、账单商户名、上传文件内容）统一贴上标签，**永远不进入指令层**。
不是用正则黑名单去「过滤关键词」——那是打地鼠。而是把「指令」和「数据」分成两条通道，数据再像指令也进不了执行路径。

**语料规模**：70 条攻击用例 + 25 条正常提问（误伤对照）
**门禁要求**：70/70 拦截 **且** 25/25 放行

> 那个「25」是刻意的。**误伤和漏拦一样是事故**——把用户正常问「你们的风控规则是什么」也拦掉，产品就没法用了。
> 扩容时正是靠这 25 条抓出一处误伤：裸「规则」二字就命中，导致业务咨询被误杀。

### 防线二：P0–P3 权限分级 —— 高危动作永久无权

`lib/gateway.js` 的 `POLICY` 表，每个动作写死级别：

> 注：**P0–P3 为内部开发代号**；在交付产品（前端界面）中已语义化呈现（如 P3 显示为「仅限本人 · 智能体无权代办」），避免向终端用户暴露内部代号，但仍严格按级别落实权限。

| 级别 | 含义 | 例子 | 智能体能做什么 |
|---|---|---|---|
| **P0** | 只读 | 查余额、查账单、查持仓 | 直接回答 |
| **P1** | 低敏写 | 创建定时转账、取消订阅、写记忆 | 申请 + 一次确认 |
| **P2** | 资金动作 | 转账、申购、赎回、锁资、挂失 | 申请 + **支付密码 + 短信** |
| **P3** | 高危不可逆 | 解绑卡、改支付密码、解绑手机、关闭安全策略 | **永久无权，只能本人操作** |

关键点：**P3 不是「暂时不支持」，是产品结论。** 把解绑卡交给一条可能被注入的链路，等于把最高危权限外包给模型。

### 防线三：HMAC 参数指纹 —— 确认的是「这一笔」，不是「转钱这件事」

`lib/util.js` 的 `signParams` / `verifyParams`

授权单生成时，把 **金额、收款人、收款账户、资源 ID（卡片/持仓/计划）** 一起签进 HMAC：

```
fingerprint = HMAC-SHA256(SIGN_KEY, canonical(params + action + userId))
展示给用户：7F3A·9C21
```

确认时用提交上来的 params 重新计算并比对，不一致直接 `status = 'tampered'`。

**为什么这一层最重要**：提示词可以让模型「别改金额」，但拦不住中间人、拦不住前端 bug、拦不住用户手误。HMAC 是**数学上改不了**，不是「约定不要改」。

演示里有一个按钮专门做这件事：**🔬 演示：篡改金额再确认** —— 点了必失败，且原单据不受影响。

### 防线四：收款人解析层 —— 不猜，是安全设计不是能力缺陷

`lib/contacts.js`

语义绕过是真实攻击手法：说「给阿姨转」，让人以为系统会自己找人。
我们的做法是**三态信任 + 只认可信通讯录**：

| 状态 | 规则 |
|---|---|
| `verified` | 可正常转账；若有同音/形近联系人，**必须提示**并要用户勾选确认 |
| `pending` | 单笔上限 **¥50**，超出拒绝；24 小时内累计大额也拒绝 |
| `unknown` | **直接拒绝**，返回两个按钮让用户自己选，绝不猜 |

解析不到就停下来问。**「系统会猜」是攻击者最喜欢的东西，我们不给。**

细节：
- 归一化用 NFKC + 剥零宽字符 + 剥标点，防「妈\u200b妈」这类变形绕过
- 同音识别用**同音表**而不是编辑距离——编辑距离会把「小红」和「小李」误判为相似
- `contactId` 是转账类动作的**必填项**，且纳入 HMAC 指纹。直接调 API 也伪造不出收款人

### 通道隔离：卡号直转与 Agent 通道物理分开

真实银行支持「填卡号即可转账」，因此转账页另设 **「卡号直转」** 入口（姓名 + 卡号 + 开户行 + 金额，无需先加联系人）。它的安全边界是**物理隔离**：

- 卡号直转**仅由用户本人在表单手填触发**，Agent / 对话通道走 `resolvePayeeGate`，**无权**把不在通讯录的卡号变成收款人——从而切断「提示词注入伪造收款卡号」的路径。
- 新卡号自动登记为 `pending` 联系人（单笔 ≤ ¥50），完成验证才恢复常规限额；已登记卡号复用信任态。
- 最终仍走 `gateway.createApproval('user', 'transfer.execute', …)` + 双因子确认，与 Agent 通道共用同一套授权单与 HMAC 指纹。

**要点**：智能体永远碰不到「任意卡号」这条路；能填卡号的只有用户本人。

### 防线五：审计哈希链 —— 日志不是「记下来」，是「改不了」

`lib/gateway.js`

每条审计记录存 `prev_hash` 与 `hash = HMAC(prev_hash | payload)`，形成链。
`verifyAuditChain()` 从头重算，任何一条被改、被删、被插，都会在断点处检出。

**一个真实修过的缺陷**：日志超 2000 条触发分级保留（关键事件留 1200 + 普通留 800），裁剪后 id 跳号，链校验报「链接断裂」。原代码注释写着「允许这种情况」，但实现里没有这个逻辑——这是一处**注释与实现不一致**的隐患。

修法：裁剪后重算 `prev_hash/hash` 重封链，并记录 `auditTrimmed`；启动自检发现历史断链时自动重封一次并留痕 `audit.reseal`，**不掩盖**。

**可视化**：顶栏常驻「🔗 审计链 完好 · N」徽标（异常变红），点击可展开链尾哈希并一键现场校验——把这道核心防护从深埋的安全中心提到了每个页面都能看见的位置。

> 这个 bug 如果不是压测把日志量顶到 2000 以上，答辩现场点「校验完整性」就会当场变红。B 组是一票否决项。

## 五、六大场景实现对照

| 场景 | 实现要点 | 交付项 |
|---|---|---|
| **S1 智能对话** | 规则 + 模型双通道；强特征意图规则优先（模型没见过新动作只会退化成闲聊）；服务端时间归一化「上个月」 | A1 |
| **S2 账单分析** | 月度汇总 + 类目下钻 + 商户/地点关键词查询；问收入时明确说明「账单只统计支出」 | A2 |
| **S3 订阅代扣** | 从账单识别周期扣费（同商户 + 金额 ±1% + 同周期间隔）；重复扣费检测；取消前影响清单；取消后衔接理财 | A3 |
| **S4 卡片管理** | 冻结/解冻/默认卡/绑定/挂失；挂失给出关联代扣与定时转账影响评估 | A4 |
| **S5 理财** | 未测评时**会话内 3 题测评卡**（不踢回页面）；测评后 3 只并列对比卡（风险/年化/期限/起投/推荐理由） | A5 |
| **S6 跨场景联动** | 记忆（强 schema）→ 计划（六步确定性状态机）→ 主动提醒（只建议不执行）→ 逆序回滚 → 虚拟时钟 | A6 |

### 5.1 S6 的关键设计：状态机不由模型编排

「帮我准备生日惊喜」的六步是**写死在代码里**的：

```
记忆 → 日历 → 锁资(P2) → 下单 → 通知 → 回执
```

模型只负责认出「用户要做这件事」，顺序和每步做什么由代码决定。
**这样「可撤销」才是结构性的**——每个写节点都自带反操作，逆序回滚即完整撤销。

如果让模型自由编排，就会出现「先下单后付钱」这种空转，以及「撤销时不知道该退什么」。

### 5.2 虚拟时钟按用户隔离

演示需要「推进 10 天看到提醒」，但全局改时间会污染所有账号的资金/审计/限速时间语义。
实现为 `db.virtualClocks[userId]`，**只影响计划的时间判断**，其他一律用真实时间。

## 六、智能体能力：上下文与自主性

### 6.1 上下文分三层

| 层 | 存什么 | 解决什么 |
|---|---|---|
| 会话槽位 | `{action, slots, missing}`，TTL 5 分钟 | 「给妈妈转」→ 追问金额 → 用户只回「100」即可继续，不用整句重说 |
| 对象栈 | 收款人/产品/计划/订阅 各一个栈顶 | 「买它」「取消它」能落到具体对象；无上下文时**不猜**，明确追问 |
| 长期记忆 | 7 类白名单 key + 类型校验 | 未存项明确回答「我还没有记住」，**不编造** |

**为什么不把对话历史整个塞进 prompt**：
token 膨胀只是小问题，真正的问题是历史里的攻击文本会成为新的注入面，而且不可审计。
结构化槽位比原始历史可靠——**该存「他说要转 100 给妈妈」，不是存「他说的那句话」**。

### 6.2 自主性六项

| 项 | 实现 |
|---|---|
| 计划可重规划 | `plan.adjust` 支持跳过/提前；**锁资禁止后置**（守资金前置约束） |
| 失败反思 | 余额不足不报错，算差额给「赎回补足 / 降额 / 预约」三分支，≤2 次反思后转人工 |
| 中断恢复 | 未确认单据压栈 + 附言提醒 + 「继续」可回，**不阻断新操作** |
| 指代消解 | 「他/她/刚才那个」→ 本会话最近收款人，按用户隔离，跨会话不猜 |
| 条件分支 | 三分支均可一键生成授权单 |
| 工具组合 | 「我卡丢了」一句话产出 4 步动作链 |

> **中断恢复这一项踩过坑**：第一版做成「有未确认单据就阻断新意图」，结果验收脚本的连续用例被拦掉 4 项。
> 这不是测试太死板，是设计错了——用户想顺手办别的事，不该被一张陈年单据挡住。改成提示式后恢复。

### 7.1 关于 D2 幻觉率的诚实说明

首轮测出 62.5%，逐条核对后分两类：

- **3 条是判定词表误伤**：「房贷需通过贷款模块查询，当前**暂不支持**」明明是诚实回答，但词表只认「暂无/没有」。这是测量工具的问题，修正词表。
- **2 条是真问题**：
  - 问「我上次去三亚花了多少」→ 直接甩整体账单 Top3，**没核实三亚有没有消费**
  - 问「我上个月工资多少」→ 拿支出总额回答收入问题，**数字是真的，语义是错的**

两处都修了：带地点/商户的查询先抽关键词，查不到就明说；收入类问题直接说明账单只统计支出。

修正后 0%。**这是修判定 + 修缺陷，不是调数字。**

## 八、工程取舍（主动说明，避免评审误判）

| 取舍 | 选择 | 理由 | 代价 |
|---|---|---|---|
| 依赖 | **零第三方依赖** | 断网可跑、无供应链风险 | 自己实现 HTTP 服务、HMAC、锁 |
| 数据 | 单文件 JSON（`data/db.json`） | 演示可 reset、可人为篡改做攻击演示 | 不是生产级存储，无事务 |
| 限速 | 进程内内存桶 | 单实例演示足够 | 多实例需换 Redis |
| 模型 | 可选，不配则降级规则引擎 | 现场无网也能演示 | 规则引擎覆盖意图有限 |
| 会话持久化 | 内存 + 落盘混合 | 简化实现 | 刷新页面靠草稿恢复，不是完整会话恢复 |
| 通讯录 | 新用户预置 5 位**示例**联系人 | 演示需要；真实产品不应预置 | 界面上已有「示例」标识与清除入口 |

## 九、已知限制（不做掩饰）

1. **忘记支付密码已支持本人人脸 + 短信双因子重置**（P3 独立通道，Agent 不可触达）：演示环境走人脸核验动画 + 一次性短信验证码重置，非生产级人工核验；正式产品仍需柜台 / 人工核验兜底。
2. **限速与锁在进程内**：重启即清空，不适合多实例。
3. **会话历史不落库**：刷新后只有草稿卡恢复，不是完整对话续接。
4. **规则引擎意图覆盖有限**：未配模型时，复杂句式会被回「没听懂」。
5. **A6 的「生日惊喜」场景偏演示性**：真实需求存疑（谁会让银行订蛋糕），做它是为了赛题「跨场景联动」的题眼。相比之下 A3 订阅、A4 挂失是真实痛点。
6. **无障碍与适老化未做**：`M1–M5` 全部假设用户能读卡片、能打字。这是明确缺口。

## 十、安全改版期间的纪律（可复用的工程实践）

改 UI 曾三次破坏功能，都记在这里：

| 事故 | 根因 | 教训 |
|---|---|---|
| 全部按钮点不动 | 开了 CSP `script-src 'self'`，内联 `onclick` 被静默拒绝 | 前端改动必须检查是否残留内联事件与 `javascript:` 伪协议 |
| 冻结卡、赎回被误拦 | 新参数校验没兜住 LLM 返回的 `{"cardId": ""}` | 校验前先回填默认资源，且资源 ID 要进 HMAC |
| 并发用例全红 | 新注册用户没有演示通讯录，转账全被解析层拒 | 新增准入层必须同步所有用户创建路径 |

**因此定的门禁**：

> 每个阶段合并前，五套回归必须**原样全绿**；
> **只允许新增用例，不允许放宽已有断言。**
> 测试是安全契约，不是障碍。
