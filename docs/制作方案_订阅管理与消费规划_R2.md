## 0. 对 R2 关键修订的理解（先对齐，再动手）

R2 相对初版（R1）推翻了一条核心假设，并新增了多条纪律。动手前必须吃透：

1. **推翻"省钱→攒钱→达成目标"资金闭环**。订阅节省（月百元级）与大额消费目标（月千元级）不在同一量级（R=7%），不能把"砍订阅"包装成"旅行基金来源"。
2. **两功能共用数据层，但不共用目的与叙事**：
   - 功能一（订阅管理增强）= 止损 / 知情权，痛点"被涨价坑了 / 钱花得不明不白"，情绪是愤怒；
   - 功能二（消费规划）= 诚实诊断，"告诉你行不行、以及要改什么才行"，情绪是焦虑。
3. **量级门槛 `R ≥ 20%` 固化成布尔量 `subSavingQualified`**：未达标时，订阅节省**不得**进入 `fundingSources`，文案只陈述事实（"订阅占月支出 2%"），**不得**接"所以可以用来……"。
4. **合规红线（两条）**：
   - `targetDate - now < 180 天` → `linkedProductId` 只允许 R1，任何 R2+ 在建单层直接拒绝；
   - **不得暗示"省小钱能达大目标"**——金额类关联必须先过 R 门槛，凑不出来的关联不造。
5. **实施依赖关系修正**：功能二**不依赖**功能一的输出（省钱额不是规划输入），三期独立，可后做。

> 本方案严格按此修订执行，初版的"闭环叙事 / 联动建单 / 主动推销订阅攒钱"一律不做。

### 1.2 `lib/store.js` —— 种子数据的缺口（关键隐患）
- 演示订阅是 `seedFor()` 写死的固定金额（云视视频会员 ¥25、悦听音乐 ¥15、云盘存储Pro ¥9），**没有价格轨迹** → N1 检不出任何涨价。
- `seedBills()` 生成的账单**不含任何订阅类商户**（只有餐饮/交通/购物/居住/娱乐），所以 `detectFor` 从账单里**识别不出订阅**，订阅只靠 demo 种子列出来。
- **结论**：N1 必须有"订阅扣费历史"种子。一期需新增 `seedSubscriptionBills(userId)`，给演示账户灌入真实的历史扣费序列（含一笔明显的涨价），否则 N1 永远是空。

### 1.3 `lib/finance.js`（我之前写的泛消费分析）—— 定位冲突，处置决定
这是 R1 思路的产物：从 `bills` 算分类占比 / 环比 / 异常 / 订阅列表 / 省钱建议。它**不是 R2 功能一的主角**（R2 功能一是订阅安全，不是泛分析）。
**处置决定（D1）**：
- 保留其为**纯函数聚合工具**，降级为功能二"支出结构透视"的底层数据源（功能二 `assess` 复用它的 `categories`/`monthly` 聚合逻辑，避免重复造轮子）。
- 账单页的"智能分析"面板**从泛分析改为订阅管理增强（N1–N5）为主角**；`finance.js` 的分类聚合仅在规划诊断卡里以"支出结构透视"名义出现，且**不附带"砍订阅能省多少"的误导文案**。
- 不在账单页展示 `finance.insights` 的"省钱建议"作为功能一卖点。

### 1.4 `lib/plans.js`（生日惊喜跨场景联动）—— 功能二执行载体的可行性
- 已有：确定性状态机（memory/calendar/escrow/order/notify/receipt）、`escrow` 锁资 + `releaseEscrow`、`rollback` 逆序回滚、`clock` 虚拟时钟、`publicView`。
- 问题：其 `STEPS` 是生日专属（memory/calendar/order），**不映射**到规划的"自动转入/申购/取消订阅"。
- **处置决定（D2）**：功能二采用"**诊断 + 执行分离**"：
  - **诊断层** = 新建 `lib/planning.js`，提供 `assess()`（P0，核心价值，独立、低风险）；
  - **执行层** = 复用 `plans.js` 的 `plan.create`(P1)/`plan.rollback`(P1) + `gateway.createStandingAuth`(自动转入 P1) + `gateway` 的 `wealth.subscribe`(P2)，并**扩展 plans.js 支持 `planning` 类型**（自带 auto_transfer / subscribe / cancel_subs 三步）。
  - 现有 `plans.js` 的 trip/goal（我之前做的 escrow 旅行规划）**保留并作为诊断后的执行载体**，不废弃。

### 1.5 `lib/gateway.js` —— 可直接复用
- `POLICY` 权限表：新增 N1–N5 与 `plan.assess` 条目（全 P0/P1，无 P3）。
- `createStandingAuth` / `checkStandingAuth`：功能二"自动转入"直接复用（范围+单日限额+有效期+随时撤销）。
- `audit` / `verifyAuditChain`：所有动作留痕；R 门槛违规的建单拒绝**必须写审计**。

```js
function detectPriceHike(userId) {
  const db = store.get();
  const bills = (db.bills||[]).filter(b=>b.userId===userId && b.amount>0 && b.source!=='deposit');
  const byM = new Map();
  for (const b of bills){ const k=String(b.merchant||'').trim(); if(!k||NOT_SUBSCRIPTION.test(k))continue;
    if(!byM.has(k))byM.set(k,[]); byM.get(k).push(b); }
  const out=[];
  for(const [m,list] of byM){
    const p = MERCHANT_PROFILES[m];
    if(p && p.billingType==='usage') continue;            // 按量计费：价格波动正常，跳过
    const sorted = list.slice().sort((a,b)=>String(a.date).localeCompare(String(b.date)));
    const n = Math.min(3, sorted.length-1);
    const baseline = median(sorted.slice(0,n).map(x=>x.amount)); // 中位数抗促销拉偏
    const current = sorted[sorted.length-1].amount;
    const hikeRatio = baseline>0 ? (current-baseline)/baseline : 0;
    const curCount = sorted.filter(x=>x.amount===current).length;
    if(hikeRatio>0.20 && curCount>=2){                    // 涨幅>20% 且当前价出现≥2次（排除一次性调价）
      out.push({ merchant:m, baseline, current, hikeRatio,
        priceTrail: sorted.map(x=>({date:x.date, amount:x.amount})),
        firstChargeAt: sorted[0].date, profile:p||null });
    }
  }
  return out;
}
```

- `listFor` / `detectFor` 增强：给每条订阅附带 `profile`（legalName/channel/billingType），供前端溯源与 N1 排除 usage。

### 三期：功能二 诊断层（核心，新建 `lib/planning.js` + `plan.assess`）

**目标**：实现"诚实的诊断"——告诉用户行不行、要改什么、什么不是瓶颈。**全部 P0，不碰钱，独立交付。**

#### 3.3.1 新建 `lib/planning.js`
核心函数 `assess(user, { category, targetDate, targetAmount })`：

1. **现金流引擎 `cashflow(userId, months=6)`**（R2 §2.5①，服务端算，绝不让 LLM 估）：
```js
function cashflow(userId, months=6){
  const db=store.get();
  const bills=(db.bills||[]).filter(b=>b.userId===userId && b.source!=='deposit' && b.category!=='转账');
  // 支出：按月聚合；收入：按月聚合 source==='deposit'（一期已埋工资种子）
  const exp = monthlySum(bills,'amount');
  const inc = monthlySum(db.bills.filter(b=>b.userId===userId && b.source==='deposit'),'amount');
  const monthsN = Math.min(months, exp.length);
  const cap = exp.map((e,i)=>(inc[i]||0)-e);
  return { incomeMedian:median(inc.slice(-monthsN)), expenseMedian:median(exp.slice(-monthsN)),
    capacityMedian:median(cap.slice(-monthsN)), capacityWorst:Math.min(...cap.slice(-monthsN)),
    sampleMonths:monthsN, method:'median_6m' };
}
```
  三条纪律：中位数（抗大额拉偏）、给最差月（不掩盖风险）、带口径（"基于近 N 月实际收支，中位数月可支配 ¥X，最差 ¥Y"）。**数据不足（<3 月账单）→ 明确回答"数据不足，无法测算"，不编造。**

2. **支出结构透视**：复用 `finance.js` 的 `analyzeSpending` 的 `categories` 聚合（或本地重算），输出 `expenseStructure[]`（category/monthly/ratio）。**订阅如实标占比（如 2%），不特殊高亮。**

3. **金额标来源**（R2 §2.5②）：旅行/大额消费给**参考区间**（`estimateRange:[min,max]`），`amountSource:'system_estimate'`；用户确认/修改后才写入 `targetAmount` + `amountSource:'user_confirmed'`。**永远不给单一精确数字。**

4. **杠杆排序**（R2 §2.3.3，按真实效力）：`levers = [时间(extend_timeline) > 目标规模(reduce_target) > 支出结构(cut_expense) > 订阅(subscription)]`。订阅排最后且标注占比。

5. **量级门槛 `subSavingQualified`**（R2 §2.3.2）：
```js
const S = subsMonthlySaving;            // 每月可省（订阅）
const M = monthsLeft; const T = targetAmount;
const R = (S*M)/T;
const subSavingQualified = R >= 0.20;   // 门槛固化成布尔
```
   未达标 → `fundingSources` 中**不得**出现 `subscription_saving`；`subSavingRatio=R` 留痕；文案只陈述"订阅占月支出 2%"。

6. **可行性 `feasibility`**：`ok | tight | infeasible`（基于 `monthlyNeed = (T/M)*1.1`（含10%缓冲）vs `capacityMedian`）。

#### 3.3.2 品类参考价表（诚实区间，非报价）
`TRAVEL_REF = { japan:[12000,15000], thailand:[4000,7000], ... }`（单位元，可配置，标"参考区间，非报价"）。

#### 3.3.3 合规红线（R2 §2.5③，写进 `assess` 与建单层）
`targetDate - now < 180天` → 若 `linkedProductId` 为 R2+，**建单层直接拒绝**；诊断文案只说"这笔钱 X 月后要用，适合 R1 灵活宝（随时可取）"，**禁收益承诺/预测**。

#### 3.3.4 接口（`server.js`）
- 新增 `POST /api/planning/assess`（P0 只读，参数 `{category, targetDate, targetAmount?}`）→ 返回诊断对象。

#### 3.3.5 意图（`lib/agent.js`）
- `INTENT_WHITELIST` 加 `'plan.assess'`(P0)。
- 规则通道：用户说"我想国庆去日本/攒钱买XX"→ `plan.assess`（LLM 只负责把自然语言译成 `{category, targetDate}`，**所有数字服务端算**）。
- `plan.create`（799 行）扩展：先走 `assess` 诊断，再让用户在诊断卡上"据此建计划"。

#### 3.3.6 前端（`public/app.js`）
- 账单页"消费规划"区（`planningSection`）重构为**诊断优先**：
  - 输入：一句目标（或模态收集 类型/目标日期/参考金额）；
  - 输出诊断卡：`可行性（可行/很紧/不可行）` + `现金流口径（中位数/最差月）` + `支出结构透视（订阅标 2%）` + `三个真实杠杆（按效力排序）` + `若未过 R 门槛：明确写"订阅不是你的瓶颈"`。
- **不推送、不暗示**：诊断卡内不做任何订阅相关推销；大额目标场景零订阅推送。

#### 3.3.7 验收用例
- "国庆去日本 7 天" → 诊断卡给出区间 ¥12,000–15,000（标参考、可改）、现金流中位数/最差月、可行性"很紧"、三杠杆、订阅标 2% 且写明"不是瓶颈"；
- 数据不足账户（<3 月账单）→ 明确"无法测算"；
- 用户问"取消订阅能帮我达成吗" → 明确"不能，真正约束是时间和结构"。

### 四期：功能二 执行层（逐项授权 + 回滚 + R 门槛校验）

**目标**：把诊断落为可执行、可撤销的计划，严守 R 门槛与合规红线。

#### 3.4.1 执行链路（复用既有，零新写资金逻辑）
- `plan.create`(P1) → 复用 `plans.js`，扩展 `planning` 类型，自带三步：`auto_transfer`(P1, `gateway.createStandingAuth`) → `subscribe`(P2, `gateway.wealth.subscribe`，仅 R1 或已过适当性) → `cancel_subs`(P1, `subscription.cancel`)。
- 每一步**独立过闸、独立授权**（对齐 `agentCall` 逐次过网关）；不能因"批准了整个规划"就批量执行。
- 回滚：`plans.rollback`(P1) 逆序回滚，复用既有 escrow 释放 + 通知/订单撤销。

#### 3.4.2 R 门槛校验（建单层，R2 §2.4）
`plan.create` 执行前校验：`if (!subSavingQualified && fundingSources 含 subscription_saving) → 拒绝建单 + 写审计（INJECTED_BLOCKED/BLOCKED，layer=POLICY）`。`cancel_subs` 步骤仅在 `subSavingQualified===true` 时出现。

#### 3.4.3 合规红线（执行层）
`targetDate-now<180天` 时，`linkedProductId` 强制 R1；若用户/链路试图选 R2+ → 建单层拒绝并触发适当性测评卡（复用 agent.js 1311 行三问）。

#### 3.4.4 前端（`public/app.js`）
- 诊断卡"据此建计划" → 调 `plan.create` → 进入既有规划执行流（逐步授权 / 一键回滚）。
- 规划卡展示：`targetAmount`(+来源标记)、`feasibility`、`fundingSources`（R 门槛过滤后）、`steps` 进度、回滚按钮。

#### 3.4.5 测试门禁（`tests/run_planning.js`）
- 现金流准确性（中位数/最差月/口径）；
- 量级门槛（R≥20% 进 fundingSources 标占比；R<20% 不进 + subSavingQualified=false）；
- 合规红线（<180天+R2 拒绝；适当性缺失触发测评；"正好覆盖需求"文案断言 R≥20% 否则失败）；
- 强制注入：R=7% 但 `fundingSources` 含 `subscription_saving` → 建单层拒绝 + 写审计。

#### 3.4.6 验收用例
- 诊断"很紧" → 建计划 → auto_transfer 授权单（P1）→ 确认 → 余额不变、冻结额增加 → 回滚 → 资金释放；
- 大额目标 + R=7% → 规划卡不出现"订阅资金来源"；
- <180 天目标选 R2 产品 → 建单被拒。

## 7. 风险与误报治理清单（照抄项目已有纪律）

1. N1 误报：按量计费跳过 / 升级有记录放行 / 大促排除 / 涨幅<20% 放行 / 首月优惠归 N5（§3.2.5）。
2. 金额幻觉：现金流、目标区间**全部服务端算**，LLM 只译自然语言（§3.3.1）。
3. 合规：<180天只许 R1；禁收益承诺；凑不出的关联不造（§3.3.3、§3.4.3）。
4. 推送克制：功能一推送仅限"涨价命中 / 到期 T-3"（用户不知情才需推）；功能二**不主动推送**订阅攒钱（§3.3.6）。
5. 误伤=漏拦：正负样本双向门禁，只测命中率会把产品逼成噪音制造机（§5）。

## 8. 答辩叙事衔接（按文档 §4，拆分两条）

- **功能一**："2025 年自动续费投诉近 7 万条、累计超 22 万条；《互联网平台价格行为规则》2026-04-10 施行，要求每次扣款前提前告知金额与取消途径；建行 2026-08 上线支付账单做溯源。我们做的不是营销功能，是帮银行履行监管要求——涨价检测给可自证的价格轨迹，扣款溯源给商户全称与取消入口。"
- **功能二**："用户说'我想国庆去日本'，他没有金融词汇只有生活计划。传统 App 要他自己完成'旅行→要花多少→能存多少'的翻译，这三步他做不了。agent 把翻译做掉，给出诚实答案：可行但很紧。更重要的是告诉用户什么不是瓶颈——订阅只占月支出 2%，砍光也解决不了日本行；真正杠杆是时间、目标规模、支出结构。阻止用户追错误的杠杆，和防止漏掉风险，是同一类价值。"
- 理性表态："所有金额服务端算非模型估算；凑不出的关联不造——省钱额占目标不足 20% 时，它不会出现在资金来源里。"
