## 一、P0-1 ｜ U-01 登录暴力破解

### 根因

`server.js:98-107` 的登录处理只有「校验 → 通过/失败」，**没有任何失败计数、没有锁定、没有延迟**。攻击者可用字典无限次尝试。

### 方案：三维限速（账号 + IP + 渐进延迟）

**① 新增内存限速表**（放 `lib/util.js` 或新建 `lib/limits.js`）

```js
// 内存计数：重启即清空，演示系统足够；生产需换 Redis
const loginFails = new Map();   // key: phone 或 ip
const LOGIN_MAX_FAILS = 5;      // 连续失败 5 次
const LOGIN_LOCK_MS   = 5 * 60 * 1000;  // 锁定 5 分钟

function loginGuard(key) {
  const rec = loginFails.get(key);
  if (!rec) return { ok: true };
  if (rec.lockedUntil && rec.lockedUntil > Date.now()) {
    return { ok: false, retryAfter: Math.ceil((rec.lockedUntil - Date.now()) / 1000) };
  }
  if (rec.lockedUntil && rec.lockedUntil <= Date.now()) loginFails.delete(key); // 到期重置
  return { ok: true };
}
function recordLoginFail(key) {
  const rec = loginFails.get(key) || { count: 0, lockedUntil: 0 };
  rec.count++;
  if (rec.count >= LOGIN_MAX_FAILS) rec.lockedUntil = Date.now() + LOGIN_LOCK_MS;
  loginFails.set(key, rec);
  return rec.count >= LOGIN_MAX_FAILS;
}
function clearLoginFail(key) { loginFails.delete(key); }
```

**② 改造登录接口**（`server.js:98`）

```js
route('POST', '/api/auth/login', async (req, res, body) => {
  const db = store.get();
  const phone = String(body.phone || '').trim();
  const ip = (req.socket.remoteAddress || 'unknown');

  // ① 账号锁定检查
  const g1 = loginGuard('phone:' + phone);
  if (!g1.ok) return json(res, 429, { ok: false, message: `密码错误次数过多，请 ${g1.retryAfter} 秒后再试` });
  // ② IP 限速检查
  const g2 = loginGuard('ip:' + ip);
  if (!g2.ok) return json(res, 429, { ok: false, message: `请求过于频繁，请 ${g2.retryAfter} 秒后再试` });

  const user = db.users.find(u => u.phone === phone);
  if (!user || !verifyPassword(body.password || '', user.passwordHash)) {
    const locked = recordLoginFail('phone:' + phone);
    recordLoginFail('ip:' + ip);
    if (user) gateway.audit(user.id, 'user', 'auth.login', {}, 'REJECTED',
      locked ? '登录密码连续错误达 5 次，账号已锁定 5 分钟' : '登录密码错误',
      locked ? '校验层' : null);
    return json(res, 401, { ok: false, message: '手机号或密码错误' });
  }
  clearLoginFail('phone:' + phone);
  // …后续不变
});
```

**③ 可选加分：失败次数越多延迟越长**

```js
// 第 n 次失败后延迟 n*150ms（最多 1.5s），让爆破成本指数上升
const delay = Math.min(count, 10) * 150;
await new Promise(r => setTimeout(r, delay));
```

### 验收标准

```bash
# 连续 5 次错误密码 → 第 6 次必须返回 429
for i in $(seq 6); do
  curl -s -o /dev/null -w "%{http_code} " -X POST localhost:3000/api/auth/login \
    -H "Content-Type: application/json" -d '{"phone":"13800000001","password":"bad"}'
done
# 期望：401 401 401 401 401 429
```

### 副作用与注意事项

- **锁定是按手机号**，需确认这不会导致「攻击者故意锁死你的账号」（DoS）。缓解：按「手机号 + IP 组合」锁定，或锁定时仍允许正确密码登录。
  - **推荐折中**：锁定后返回 429，但**若密码正确则放行并清零计数**——既防爆破又不给攻击者「锁死别人账号」的能力。
- 演示时如果要展示这条能力，需要**先准备独立的测试账号**，不要用主演示账号试，否则会把自己锁 5 分钟。

## 二、P0-2 ｜ U-16 / U-17 验证码与支付密码试错

### 根因

`lib/gateway.js:193-207` 的确认逻辑里，支付密码错、验证码错都只是「返回错误并写审计」，**授权单状态仍是 `pending`，计数器不存在**。攻击者可对同一张单无限重试 6 位数字（验证码）或 6 位支付密码。

这是整个体系里**最危险的一个洞**：P2 是资金操作，第二道门可被暴力拆开。

### 方案：单次授权单「共享失败计数 + 3 次锁单」

**设计要点**：
- 支付密码与验证码**共用**一个 `attemptCount`（防止「两种各试 5 次」绕过）
- 达 3 次 → 授权单置 `status='locked'`，**立即作废**，必须重新发起
- 同时按用户累计计数，10 分钟内 5 次锁单 → 冻结该用户资金操作 15 分钟（防「不断新建单据刷次数」）

**① 授权单增加字段**（`lib/gateway.js:126-135` 创建处）

```js
const approval = {
  // …原有字段
  attemptCount: 0,          // 新增：本单累计失败次数
  lastAttemptAt: null,      // 新增：最后一次尝试时间
};
```

**② 确认逻辑改造**（替换 `lib/gateway.js:193-207`）

```js
// ② 校验层：失败次数上限（放在密码校验之前，避免"锁单后还能试一次"）
const MAX_ATTEMPTS = 3;
if ((ap.attemptCount || 0) >= MAX_ATTEMPTS) {
  ap.status = 'locked';
  store.save();
  const log = audit(user.id, 'gateway', ap.action, {}, 'BLOCKED',
    `授权单验证失败次数达上限（${MAX_ATTEMPTS} 次），单据已作废，需重新发起`, LAYER.VERIFY);
  return blocked(LAYER.VERIFY, `验证失败次数过多（${MAX_ATTEMPTS} 次），该授权单已作废，请重新发起操作`, log);
}

// 统一失败出口：累加计数 → 达阈值锁单
function failAttempt(reason) {
  ap.attemptCount = (ap.attemptCount || 0) + 1;
  ap.lastAttemptAt = Date.now();
  const exceeded = ap.attemptCount >= MAX_ATTEMPTS;
  if (exceeded) ap.status = 'locked';
  store.save();
  const log = audit(user.id, 'user', ap.action, {}, 'REJECTED',
    exceeded ? `${reason}（第 ${ap.attemptCount} 次，已达上限，授权单作废）` : `${reason}（第 ${ap.attemptCount}/${MAX_ATTEMPTS} 次）`,
    LAYER.VERIFY);
  return blocked(LAYER.VERIFY,
    exceeded ? `${reason}；失败次数已达上限，该授权单已作废，请重新发起` : `${reason}，还可尝试 ${MAX_ATTEMPTS - ap.attemptCount} 次`,
    log);
}

if (ap.level >= 2) {
  if (!cred || !cred.payPassword || !cred.smsCode) return { ok: false, message: '需要支付密码和短信验证码' };
  if (!user.payPasswordHash || !verifyPassword(cred.payPassword, user.payPasswordHash)) {
    return failAttempt('支付密码错误');
  }
  const sms = db.smsCodes.filter(s => s.approvalId === ap.id && s.expiresAt > Date.now()).pop();
  if (!sms || sms.code !== String(cred.smsCode).trim()) {
    return failAttempt('短信验证码错误或已过期');
  }
  // 验证成功 → 消费验证码（一次性，防复用）
  if (sms) sms.usedAt = Date.now();
}
```

**③ 用户级累计（防「换单刷次数」）**

```js
// 复用 U-01 的 loginGuard，key 换成 'pay:' + user.id
const g = loginGuard('pay:' + user.id);
if (!g.ok) return blocked(LAYER.VERIFY, `支付验证失败过多，请 ${g.retryAfter} 秒后再试`, null);
// 每次 failAttempt 内同步调用 recordLoginFail('pay:' + user.id)
// 阈值：10 分钟 5 次 → 冻结 15 分钟（可用独立常量）
```

**④ 已作废单的状态处理**：`ap.status === 'locked'` 时，前端应显示「此单据已作废，请重新发起」，并禁用确认按钮。

### 验收标准

```bash
# 同一授权单连续 3 次错误验证码 → 第 3 次返回 blocked 且 status=locked
# 第 4 次再试 → 直接拒绝（"授权单状态为 locked"）
for i in 1 2 3 4; do
  curl -s -X POST localhost:3000/api/approvals/$APID/confirm \
    -H "Content-Type: application/json" -H "X-Token: $TOKEN" \
    -d '{"payPassword":"123456","smsCode":"00000'$i'"}' | grep -o '"message":"[^"]*"'
done
# 期望第 3 次后单据作废，第 4 次提示已作废
```

### 影响现有测试

`tests/smoke.js` 第 5 项「确认执行」用的是正确验证码，第一次即成功，**不受影响**。
但若测试里有「先故意错一次再正确」的流程，会消耗 1 次机会——需检查并调整顺序。

## 三、P1-1 ｜ U-28 / U-29 授权单创建不校验参数

### 根因

`lib/gateway.js:110` 的 `createApproval` 拿到 `params` 后**直接签名建档**，没有任何合法性校验。实测 `-100`、`0`、`abc`、`1e5`、`999999999999`、理财 `-500` 全部能创建 P2 单据并触发短信。

虽然执行层 `toCents()` 会拦，但已造成：① 垃圾授权单堆积（上限 500 条自动裁剪，会挤掉有效单）；② 无意义短信，可被骚扰式刷屏；③ 审计污染（每单至少 2 条日志）。

### 方案：按 action 定义参数 schema，入口统一校验

**① 在 `POLICY` 表旁增加校验规则**

```js
// 参数校验规则：与 POLICY 同级维护（安全决策不经过 LLM）
const PARAM_RULES = {
  'transfer.execute':  { amount: 'money', toName: 'name' },
  'scheduled.create':  { amount: 'money', toName: 'name', freq: 'enum:once,daily,weekly,monthly' },
  'aa.create':         { total: 'money', title: 'text', participants: 'text' },
  'wealth.subscribe':  { amount: 'money', productId: 'id' },
  'wealth.redeem':     { holdingId: 'id' },
  'card.freeze':       { cardId: 'id' },
  // P1 的其他动作按需补
};

const VALIDATORS = {
  money: (v) => {
    const n = Number(String(v).replace(/[,，\s]/g, ''));
    if (!Number.isFinite(n) || n <= 0) return '金额必须为正数';
    if (n > 500000) return '金额超出合理上限';
    if (Math.round(n * 100) !== Number((n * 100).toFixed(6))) return '金额最多两位小数';
    return null;
  },
  name: (v) => (String(v || '').trim().length === 0 || String(v).length > 50) ? '收款人名称非法' : null,
  text: (v) => (String(v || '').length > 200) ? '文本过长（上限 200 字）' : null,
  id:   (v) => (/^[\w-]{1,64}$/.test(String(v || '')) ? null : 'ID 格式非法'),
};

function validateParams(action, params) {
  const rules = PARAM_RULES[action];
  if (!rules) return null;                       // 未定义规则的动作不额外校验
  for (const [key, rule] of Object.entries(rules)) {
    if (rule.startsWith('enum:')) {
      const allowed = rule.slice(5).split(',');
      if (params[key] && !allowed.includes(params[key])) return `参数 ${key} 取值非法`;
      continue;
    }
    if (params[key] === undefined || params[key] === null || params[key] === '') {
      if (key === 'amount' || key === 'toName' || key === 'total') return `缺少必要参数：${key}`;
      continue;
    }
    const err = VALIDATORS[rule] && VALIDATORS[rule](params[key]);
    if (err) return err;
  }
  // 金额统一规范化（解决 1.0000001 静默截断）
  if (rules.amount !== undefined && params.amount !== undefined) {
    params.amount = String(Math.round(Number(params.amount) * 100) / 100);
  }
  return null;
}
```

**② 在 `createApproval` 开头插入校验**（`lib/gateway.js:110` 之前）

```js
const vErr = validateParams(action, params);
if (vErr) {
  const log = audit(user.id, 'gateway', action, params || {}, 'BLOCKED',
    `参数校验失败：${vErr}`, LAYER.VERIFY);
  return blocked(LAYER.VERIFY, `操作参数不合法：${vErr}`, log);
}
```

### 验收标准

```bash

for a in "-100" "0" "abc" "1e5" "1.0000001" "999999999999"; do

    -d '{"action":"transfer.execute","params":{"toName":"小红","amount":"'$a'"}}'
done
# 另测理财负数、AA 空参与人

# 回归：正常金额必须仍能创建
curl -s -X POST localhost:3000/api/ops/request -H "X-Token: $TOKEN" \
  -H "Content-Type: application/json" \
  -d '{"action":"transfer.execute","params":{"toName":"小红","amount":"100"}}'
# 期望：ok:true，生成 P2 单据
```

### 注意事项

- **`1.0000001` 的处理**：两种策略可选 —— ① 直接拒绝（严格）；② 规范化为 `1.00` 并在卡片上显示规范值（友好）。**建议 ②**，同时前端输入框限制两位小数。
- **LLM 解析出的金额**也走同一入口，因此这条校验同时保护了「LLM 输出异常值」的场景，是双重收益。
- **不要**把金额上限写死成和 `user.limits.single` 一样的语义——限额属于风控（执行层），这里只做「格式合理性」，避免职责重叠导致演示时提示混乱。

## 四、P1-2 ｜ U-36 点击劫持与响应头加固

### 根因

`server.js:27`（`json()`）与 `server.js:54`（`serveStatic()`）两处 `res.writeHead()` 都只设了 `Content-Type`，**没有任何安全响应头**。攻击者可用 iframe 嵌套确认页实施点击劫持。

### ⚠️ 落地前必须处理的前置问题：页面有内联脚本

已核实：`public/index.html:14-57` 有 **44 行内联 `<script>`**，定义了 `$`、`app`、`LS`（存储降级封装）、`S`（全局状态）等基础变量，`app.js` 依赖它们。

**若直接上 `script-src 'self'`，这段内联脚本会被浏览器拒执行 → `app.js` 一加载就报 `$ is not defined` → 整个页面白屏。**
这是最容易踩的坑，且症状和「登录不进去」一模一样，排查会绕很久。

**三种处理方式，按推荐顺序：**

| 方案 | 做法 | 评价 |
|---|---|---|
| **① 拆出外部文件（推荐）** | 把这 44 行移到 `public/boot.js`，`<script src="/boot.js"></script>` 放在 `app.js` 之前 | 改动小、CSP 可全开、最干净 |
| **② CSP 加 nonce** | 服务端每次渲染给内联脚本发一次性 nonce，CSP 里写 `script-src 'self' 'nonce-xxx'` | 需把 index.html 改成动态渲染，改动大 |
| **③ 临时放宽** | `script-src 'self' 'unsafe-inline'` | 5 分钟能上线，但**削弱了 CSP 的 XSS 防护价值**，不推荐长期用 |

**建议**：先做 ①（约 10 分钟），再做 CSP。若时间紧张，可先只上 `X-Frame-Options` + `nosniff`（这两条不受内联脚本影响），CSP 随后补。

### 方案：两个出口统一加安全头

```js
// server.js 顶部定义
const SEC_HEADERS = {
  'X-Frame-Options': 'DENY',
  'X-Content-Type-Options': 'nosniff',
  'Referrer-Policy': 'no-referrer',
  'Content-Security-Policy': "default-src 'self'; img-src 'self' data:; style-src 'self' 'unsafe-inline'; script-src 'self'; frame-ancestors 'none'",
  'Cache-Control': 'no-store'
};
```

**修改点 ①**（`server.js:27` `json()`）：
```js
res.writeHead(code, { ...SEC_HEADERS, 'Content-Type': 'application/json; charset=utf-8', 'Content-Length': Buffer.byteLength(body) });
```

**修改点 ②**（`server.js:54` `serveStatic()`）：
```js
res.writeHead(200, { ...SEC_HEADERS, 'Content-Type': MIME[path.extname(file)] || 'application/octet-stream' });
```

### 注意事项（重要）

- **CSP 里的 `script-src 'self'` 会拦截内联 `<script>`**。已核实 `public/index.html:14-57` 确实有内联脚本，**直接加会白屏**——必须先按上一节「前置问题」拆出 `boot.js`。
- 检查命令：
  ```bash
  grep -n "<script>" public/index.html
  # 改造后应只剩下 <script src="/boot.js"> 与 <script src="/app.js">
  ```
- 之前修过的「受限环境 localStorage 崩」问题在 CSP 下不受影响（那是运行时权限，不是 CSP）。

### 验收标准

```bash
curl -sI localhost:3000/ | grep -iE "x-frame|content-security|nosniff"
# 应有 3 行输出
```

## 五、P1-3 ｜ U-11 让「改金额再确认 → 拦截」可演示

### 背景（这不是漏洞，是演示能力缺失）

方案 C 组把「改金额被拦」列为「最有杀伤力」的演示点，但当前 `confirmAndExecute(user, id, cred)` **完全不读 `cred.params`**，参数恒以服务端授权单为准。我实测客户端硬塞 `amount=99999`，结果仍只转 50 元并**提示成功**——现场演出来会很尴尬。

### 两个可选方案（需你决策）

#### 方案 A：增加「参数比对」路径（推荐，改动小）

在 `confirmAndExecute` 的签名校验之后、密码校验之前，插入：

```js
// ③ 校验层：客户端回传参数与授权单比对（演示"改金额被拦"的能力，同时保留防御价值）
if (cred && cred.params) {
  const expect = canonical(ap.action, ap.params);
  const actual = canonical(ap.action, cred.params);
  if (expect !== actual) {
    ap.status = 'tampered';
    const log = audit(user.id, 'gateway', ap.action, {}, 'BLOCKED',
      `确认参数与授权单不一致（期望 ${ap.fingerprint}，实际参数已变更），疑似篡改，已拦截`, LAYER.VERIFY);
    store.save();
    return blocked(LAYER.VERIFY, '操作参数与授权单不一致（疑似篡改），已拦截并记录安全日志', log);
  }
}
```

**优点**：改动约 15 行，复用已有 `canonical()` 与 `LAYER.VERIFY`，演示时前端加一个「篡改请求」按钮即可。
**代价**：从「没有篡改入口」退到「有入口但能拦住」。安全性并未下降（原本就拦得住），只是防控点前移。

#### 方案 B：不改代码，改演示脚本

不演「改金额」，改演**「服务端授权单被篡改」**：用一段 Node 脚本直接改 `db.approvals` 里的金额再确认，展示指纹校验拦截。

**优点**：零代码改动，不动生产逻辑。
**代价**：需要开终端跑脚本，观感不如页面内按钮流畅；且评委可能质疑「改库」不真实。

### 建议

**答辩用 A，日常提交用 B 保底**。若担心「降低安全叙事」，可在演示时明确说：「我们的确认接口默认不接受任何客户端参数；这里为了演示参数篡改攻击，特意开启了一条受控比对路径——**它的存在本身就是为了证明篡改会被拦住**。」这个说法反而能加分。

### U-14 上传内容长度上限

`lib/gateway.js` 的账单上传入口，或 `server.js` 的 `/api/bills/upload`：

if (String(body.content || '').length > 1024 * 1024) {

另：`collectBody` 已有 `data.length > 1e6` 直接 destroy（`server.js:19`），但 destroy 是断连接而非返回 413，体验上可优化为「先回 413 再断」。

### U-41 审计日志防刷爆

当前 `lib/gateway.js:63`：超 2000 条裁到 1000 条，**安全关键事件也会被裁掉**。

建议改为「分级保留」：

```js
const CRITICAL = new Set(['INJECTED_BLOCKED', 'BLOCKED', 'tampered']);
if (db.auditLogs.length > 2000) {
  const critical = db.auditLogs.filter(l => CRITICAL.has(l.result));
  const normal   = db.auditLogs.filter(l => !CRITICAL.has(l.result));
  // 关键事件全留，常规事件只留最近 800 条
  db.auditLogs = [...critical, ...normal.slice(-800)].sort((a, b) => a.id - b.id);
}
```

**风险提示**：裁剪后 `prev_hash` 链会「跳段」，`verifyAuditChain` 需要允许「首条 prev_hash 指向被裁剪的前驱」的情况——当前实现已考虑了这点（注释明确写了），但裁剪逻辑改动后要**重跑链校验**确认不误报。

### U-15 黑名单归一化

```js
function normName(s) {
  return String(s || '')
    .normalize('NFKC')          // 全角→半角
    .replace(/[\s\u200b-\u200f•.\-_]/g, '')  // 去空格、零宽字符、常见分隔符
    .toLowerCase();
}
// 匹配时：normName(toName).includes(normName(blackword))
```

注意：归一化后 `黑客.`、`黑 客`、`ｈａｃｋｅｒ` 都能命中；但**谐音/拼音无法覆盖**，需明确这是「规则匹配」而非「智能识别」，答辩时可主动说明边界。

### U-34 XSS 全量审计

grep -n '\${' public/app.js | grep -v 'esc(' | grep -v 'yuan(' | grep -v 'fmtT('
