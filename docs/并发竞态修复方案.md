# 并发竞态修复方案（U-19 / U-33）

> **基于**：`8b1c9c3` 实测 ｜ 关联清单：`docs/用户端攻击预演自查清单.md` U-19、U-33
> **范围**：并发双花（同一授权单重复扣款）、并发重复退款、并发调度重复执行
> **原则**：零依赖、不改架构、不破坏已有安全能力（28/28 注入用例 + 9 项冒烟必须保持全绿）
> **落地日期**：2026-10-17

---

## 一、先说清楚「竞态」到底是什么

### 1.1 一句话版本

**两个人（或两个请求）在同一瞬间都看到了「这笔钱还没转」，于是都转了。**

### 1.2 为什么会发生：用买菜打比方

假设你和室友共用一张银行卡，卡里 1000 元，你们同时去两个收银台刷这笔钱。

```
时间   你（收银台A）              室友（收银台B）
 │
 1     查询余额 = 1000
 2                                查询余额 = 1000   ← 此时你还没扣，他也看到 1000
 3     够付 → 扣 800
 4                                够付 → 扣 800     ← 两边都判定"够付"
 5     余额 = 200
 6                                余额 = 200        ← 后写的覆盖了前一个
 ─────────────────────────────────────────────────
 结果：卡里只少了 800，但你们各拿走了 800 元的货
```

问题的本质不是「算错了」，而是**「查余额」和「扣款」这两个动作之间，被别人插了进来**。

### 1.3 在 AgentBank 里的具体形态

我们的资金操作是「授权单」模式：

```
用户点"确认" → 服务端处理：
   ① 找到授权单
   ② 检查状态是不是 pending        ← 检查
   ③ 验签名、验支付密码、验短信码
   ④ 扣款、写流水
   ⑤ 状态改成 used                  ← 使用
```

两个请求同时打进来，都在第 ②步读到 `pending`，于是都往下走到第 ④步 —— **一笔钱扣两次**。这在安全领域叫「双花」（double spending）。

> 注意：这不是「防御被绕过」，而是**同一个合法操作被重复执行**。攻击者不需要破解任何密码，只要在点击确认的一瞬间并发多发几个请求即可。

### 1.4 为什么之前没暴露出来

原来 `confirmAndExecute` 是**纯同步函数**：从第 ①步到第 ⑤步中间没有任何 `await`。Node.js 是单线程，同步代码执行期间不会切去处理别的请求，所以天然不可能被插队。

但这是**「碰巧安全」，不是「保证安全」**：
- 一旦以后在临界区里加入任何异步操作（异步风控查询、外部支付网关回调、`await store.save()` 改成异步落盘），立刻就有漏洞
- 一旦部署成多实例（PM2 cluster、K8s 多副本），两个进程各有各的事件循环，同步也救不了
- 一旦有人把 `confirmAndExecute` 改成 `async` 并在中间 `await` 了什么，同样立刻出事

我们要做的是把「碰巧安全」变成「显式保证」。

## 二、修复方案：三层保护

思路和真实银行一样：**不指望单点拦住，而是让每一层都独立成立**。

```
请求进来
   │
   ├─ 第①层 幂等键      ── 同一个授权单 ID 只执行一次（已有的任务 E 能力）
   │
   ├─ 第②层 状态前置    ── 进临界区第一件事：pending → processing
   │                        后来者读到的已不是 pending，直接被拒
   │
   └─ 第③层 互斥锁      ── 同一时刻只允许一个请求在临界区内（本次新增）
                           锁被占 → 立即返回"处理中"，不排队
```

### 2.1 第①层：幂等键（已有，保留）

`lib/banking.js` 里 `doTransfer` 以 `approval.id` 作为幂等键，同一张单执行第二次时命中缓存，返回首次结果，**不扣款**。

这一层能挡住「顺序重复提交」（用户手抖连点两下），但挡不住「并发」——两个请求可能同时通过「幂等键不存在」的检查。

### 2.2 第②层：状态前置 processing（新增）

把授权单状态从 `pending` 直接改成 `processing`，作为**进入临界区的门票**。

```js
ap.status = 'processing';   // 临界区第一件事，之后才开始校验签名和凭证
...
// 任一环节失败 → 退回 'pending'（用户可重试）
// 成功 → 'used'；参数被篡改 → 'tampered'
```

关键点：`pending → processing` 这一步是**同步的**，中间没有 `await`，所以两个并发请求不可能都读到 `pending`。

即使以后加了锁又被绕过，这一层仍然成立——这是「纵深防御」的意义：**不依赖任何单一机制**。

### 2.3 第③层：互斥锁（本次新增 `lib/lock.js`）

```js
const lock = require('./lock');

async function confirmAndExecute(user, approvalId, cred) {
  return lock.mutex('approval:' + approvalId,
    () => confirmAndExecuteLocked(user, approvalId, cred),
    { busyMessage: '该授权单正在处理中，请勿重复提交（并发保护已生效，未发生重复扣款）' });
}
```

**设计选择：锁被占用时「立即失败」而不是「排队等待」。**

这是一个有意的取舍：

| 方案 | 用户体验 | 安全后果 |
|---|---|---|
| 排队等待 | 第二个请求等 1 秒后也执行 | ❌ 又变成双花 |
| 立即失败（本方案） | 提示"正在处理中，请勿重复提交" | ✅ 只执行一次 |

对资金操作来说，**让用户重试一次的成本，远低于多扣一笔钱的成本**。

锁的名字用 `approval:<id>`，粒度到单张授权单 —— 用户 A 的转账和用户 B 的转账互不阻塞，不会因为并发保护把整个系统串行化。

### 2.4 业务层的同步临界区

`doTransfer` 内部的「读余额 → 判断够不够 → 扣款 → 写流水」也必须整体完成：

```js
function doTransfer(user, params, opts) {
  return lock.sync(() => doTransferInner(user, params, o));   // 同步临界区，禁止 await
}
```

`lock.sync()` 同时做了一件防呆的事：**如果在临界区内又调用了 `sync()`，直接抛错**。这是为了防止将来有人不小心把临界区嵌套起来，产生隐蔽的副作用。

### 2.5 撤销接口（U-33）同样处理

```js
if (t.revoked) return { ok: false, message: '该笔转账已撤销过' };
t.revoking = true;             // 状态前置
...
acc.balance += t.amount;       // 只退一次
t.revoked = true;
```

10 个并发撤销请求，只有第一个能通过检查，后面 9 个都读到「已撤销」或「正在撤销中」。

### 2.6 顺带修掉的一个真实 bug（并发调度重复执行）

写测试时发现的，**与并发无关、但后果同样是重复扣款**：

`POST /api/scheduler/tick` 是演示用的「立即执行」按钮，传 `force=true`。原逻辑在 `force` 模式下**看完不推进 `nextRun`**，于是：

```
第 1 次 tick → 任务执行，nextRun 仍是过去的时间
第 2 次 tick → 同一任务又命中，再执行一次
第 3 次 tick → 再来一次……
```

演示现场如果主持人多点两下「立即执行」，就会反复扣款。已在 `schedulerTick` 里修复：`force` 模式下执行后一律把 `nextRun` 推到未来。

## 五、这不能解决什么（诚实说明）

**进程内锁只防「单实例并发」。**

如果将来部署成多实例（PM2 cluster / K8s 多副本 / 负载均衡后多个 Node 进程），每个进程都有自己的 `held` Map，A 进程的锁拦不住 B 进程的请求。

生产环境的正确做法是**把锁下沉到数据层**：

| 方案 | 做法 | 适用 |
|---|---|---|
| 数据库行锁 | `SELECT ... FOR UPDATE` 锁住该授权单行，事务内完成校验+扣款+改状态 | 关系型数据库（推荐） |
| 条件更新 | `UPDATE approvals SET status='used' WHERE id=? AND status='pending'`，看影响行数是否为 1 | 最简单有效，任何数据库都支持 |
| 分布式锁 | Redis `SET NX PX` 或 Redlock | 高并发、多语言环境 |

其中**「条件更新」是最值得学的**：它把「检查」和「使用」合并成一条原子 SQL，数据库引擎保证只有一个请求能更新成功。本质上就是我们第②层状态前置的数据库版本。

**参赛定位建议**：答辩时明确说「单实例用进程内锁，多实例要下沉到数据库行锁/条件更新，我们的第②层状态前置就是条件更新的应用层预演」——这种「知道边界在哪」的表达，比声称「已经完全解决」更有说服力。

另一个诚实的边界：**锁不能防止「两个不同的授权单同时扣同一笔余额」**。比如余额 1000 元，同时发起两笔 800 元的转账（两张不同的授权单）。这个场景由 `doTransfer` 里的同步临界区 + `acc.balance < amount` 检查兜住，实际不会超额。但如果将来扣款逻辑变成异步的，这里也需要加账户级锁（`lock.mutex('account:' + userId)`）。

## 六、答辩话术（可直接用）

> **问：你们怎么防重复扣款？**
>
> 三层。第一层是幂等键，同一个授权单只执行一次，但幂等键挡不住并发。第二层是状态前置——进临界区第一件事就把「待确认」改成「处理中」，两个并发请求不可能都读到「待确认」。第三层是互斥锁，同一时刻只允许一个请求在临界区里，锁被占就立即返回「处理中」，不排队。
>
> **问：为什么锁被占要立即失败，不排队？**
>
> 因为排队等于让第二个请求也执行，那就还是双花。对资金操作来说，让用户重试一次的成本，远低于多扣一笔钱。
>
> **问：多实例部署怎么办？**
>
> 进程内锁只能防单实例。多实例要下沉到数据库——最简单的是条件更新：`UPDATE approvals SET status='used' WHERE id=? AND status='pending'`，看影响行数是不是 1。我们的第二层「状态前置」就是这条 SQL 在应用层的预演，思路是一致的。
