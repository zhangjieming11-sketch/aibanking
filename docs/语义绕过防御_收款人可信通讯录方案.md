> **对应问题**：用户端攻击预演 U-03 / U-04 / U-07「语义绕过」类
> **基于**：`d9ee1a1`（并发竞态修复后）｜ 前置文档：`docs/用户端攻击预演自查清单.md`
> **产品决策来源**：2026-10-17 与项目负责人确认的四条原则（见 §1.2）

## 0. 一句话概括

**给 Agent 装一本「用户亲手验证过的通讯录」——它只能从这本册子里取人，取不到就停下来问，取到像的就提醒你核对，取到新的就先小额试。**

---

## 1. 设计目标与约束

### 1.1 我们要解决什么

当前系统的转账链路是这样的：

```
用户说"给小红转 100 元"
  → parseIntent 提取 toName = "小红"（纯字符串，无任何校验）
  → 生成授权单 params: { toName: "小红", amount: "100" }
  → 确认表单显示：收款人 小红 / 金额 ¥100
  → 用户输密码 + 验证码 → 转账成功
```

**问题在于 `toName` 是个没有根基的字符串。** 它不指向任何真实的人，没有人验证过它，它甚至可以是攻击者塞进来的任何内容。Agent 说"我转给小红了"，可"小红"是谁？账号多少？用户无从核对。

语义绕过的本质就在这里：**攻击者不需要破解任何密码，只需要让 Agent 把"妈妈"解析到骗子的账号上。** 用户看到的确认表单写着"妈妈"，点下去钱就到了骗子手里。

### 1.2 已确认的四条产品决策

| # | 决策 | 设计含义 |
|---|---|---|
| 1 | Agent 必须保留"解析代称→填出账号"的能力，否则失去接入 Agent 的意义 | **不退回手动选人**。全自动流程保留，安全靠"身份可见 + 准入验证"而非"增加操作" |
| 2 | 用户在确认表单时自行核对账号；易混淆账号需特殊标注 | 确认表单**必须展示真实姓名 + 脱敏账号 + 手机号 + 验证状态**；相似联系人自动打红标 |
| 3 | 通讯录没有此人 → Agent 直接拒绝，不做猜测 | 严谨优先于智能。拒绝时给出**引导**（一键添加），而不是死路 |
| 4 | 新账号允许转账，但"分两步"与"低限额"同时执行 | 待验证收款人：单笔 ≤ ¥50，且首次仅登记、需异渠道核对后才可提额 |
| 5 | 添加联系人必须有验证程序 | **验证是 P3 级权限，Agent 永远不能自己把联系人标记为已验证** |

### 1.3 体验设计的最高原则

> **歧义才打断，无歧义不打扰。**

这是整个方案体验好坏的分水岭。用户明确反对"频繁手动操作"，所以：

- 无歧义（通讯录里只有唯一一个"妈妈"）→ **一步不停**，直接生成授权单，身份信息在单据里展示
- 有歧义（两个"李总"、谐音相近、未登记）→ **才停下来问**，且问的时候把候选摆出来让用户一键点选

这样 90% 的正常路径毫无摩擦，10% 的异常路径才需要用户参与。

## 2. 核心设计：收款人三态模型

这是本方案的骨架。把"收款人"从**一个字符串**升级为**一个有三种状态的对象**。

```
                        ┌─────────────────────────────────┐
   用户说"给妈妈转账"  → │   代称解析（lib/contacts.js）    │
                        └────────────────┬────────────────┘
                                         │
                    ┌────────────────────┼────────────────────┐
                    ▼                    ▼                    ▼
        ┌───────────────────┐ ┌───────────────────┐ ┌───────────────────┐
        │  ✅ 已验证         │ │  🔶 待验证        │ │  ❌ 未登记        │
        │  verified         │ │  pending          │ │  unknown          │
        ├───────────────────┤ ├───────────────────┤ ├───────────────────┤
        │ 用户亲手添加       │ │ 历史转账沉淀      │ │ 通讯录里查无此人  │
        │ 且完成验证流程     │ │ 或用户刚添加      │ │                   │
        │                   │ │ 或刚换了新账号    │ │                   │
        ├───────────────────┤ ├───────────────────┤ ├───────────────────┤
        │ 单笔：用户自定限额 │ │ 单笔：≤ ¥50       │ │ 直接拒绝          │
        │ 展示：全身份信息   │ │ 展示：红色警示框  │ │ 引导添加联系人    │
        │ 体验：丝滑         │ │ 体验：警示+引导   │ │ 体验：给出出路    │
        └───────────────────┘ └───────────────────┘ └───────────────────┘
```

### 2.1 三态对照表

| 维度 | 已验证 verified | 待验证 pending | 未登记 unknown |
|---|---|---|---|
| **来源** | 用户添加 + 完成验证 | 历史转账沉淀 / 用户添加未验证 / 更换新账号 | 通讯录无匹配 |
| **单笔上限** | 用户自定（默认 ¥50,000） | **¥50** | —（拒绝） |
| **单日上限** | 用户自定（默认 ¥200,000） | **¥50** | — |
| **确认表单** | 绿标「✅ 已验证 · 2026-08-12 短信回填」 | 红框「🔶 该收款人尚未验证，单笔限 ¥50」 | 不生成单据 |
| **Agent 话术** | "已为你找到妈妈（张桂芳）" | "「阿姨」还没验证，这笔最多转 ¥50" | "通讯录里没有「阿姨」" |
| **用户动作** | 输密码+验证码即可 | 可转小额；提额需先验证 | 一键添加 / 换一个人 |

### 2.2 为什么是三态而不是二态

二态（有/无）会逼你选边站：

- 只有"有/无"→ 新认识的人第一次转账就被完全拒绝，体验很差，用户会绕开系统
- **三态给了一条中间路**：不熟的人可以先转 ¥50 应急（覆盖真实场景：同事代付、小额还款），但要转大额必须先验证

这条中间路既守住了底线（大额必须验证），又不把用户逼到墙角。**这是安全与体验最好的平衡点。**

### 2.3 待验证状态的自动沉淀

历史转账过的收款人，自动进入通讯录的"待验证"区：

```
用户向"小李"转过 3 次账（发生在通讯录功能上线前）
  → 系统自动建一条 pending 记录：{ alias: '小李', verified: false, transferCount: 3 }
  → 转账页提示：「小李」已向你转账记录中出现 3 次，完成验证后可提高限额 [去验证]
```

**把"安全限制"包装成"提额机会"**，而不是"你不能做"。这是体验精进的关键手法——同一件事，说法不同，用户感受天差地别。

## 3. 数据模型

### 3.1 联系人结构 `db.contacts[]`

```js
{
  id: 'ct' + uid().slice(0,8),
  userId: 1,

  // —— 身份 ——
  realName: '张桂芳',              // 真实姓名（确认表单主展示）
  account: '6222020200112233445',  // 完整账号（服务端存储，展示时脱敏）
  phone: '13800001111',

  // —— 代称（多个，用户自己登记）——
  aliases: ['妈妈', '妈', '老妈', '母亲'],

  // —— 信任状态（三态核心）——
  trust: 'verified',               // verified | pending | blocked
  verifyMethod: 'sms_backfill',    // sms_backfill | micro_transfer | null
  verifiedAt: 1754985600000,
  verifiedBy: 'user',              // 恒为 'user'（Agent 永不出现在此字段）

  // —— 元数据 ——
  createdAt: 1754900000000,
  createdBy: 'user',               // user | system（历史沉淀为 system）
  transferCount: 12,               // 累计转账笔数（供关系时长展示）
  firstTransferAt: 1754985600000,
  lastTransferAt: 1760000000000,

  // —— 风控 ——
  note: '',                        // 用户备注
  recentAddedRisk: false           // 是否"刚添加就大额转账"（风控信号）
}
```

### 3.2 为什么 `verifiedBy` 恒为 `user`

这是防御"通讯录污染"的技术锁。即使将来有人给 Agent 加了"添加联系人"的工具，这个字段也写死为 `user`，并在代码注释里标明：

```js
// Agent 永远不能把联系人标记为已验证 —— 这是 P3 级权限。
// 验证的本质是"用户用通讯录之外的渠道确认过对方身份"，
// 这个确认动作天然不可能由 Agent 代替完成。
```

### 3.3 种子数据（演示用）

给 demo 账户 `13800000001` 预置：

| 代称 | 真实姓名 | 状态 | 演示用途 |
|---|---|---|---|
| 妈妈、妈、老妈 | 张桂芳 | ✅ 已验证 | 正常路径，展示身份卡 |
| **妈玛** | 李梅 | ✅ 已验证 | **易混淆演示**：与"妈妈"谐音 |
| 房东 | 王强 | ✅ 已验证 | 定时转账场景 |
| 小红 | 小红 | ✅ 已验证 | 现有演示脚本兼容 |
| 同事小李 | 李强 | 🔶 待验证 | 低限额 + 引导验证 |
| — | — | — | 通讯录里**故意不放**"阿姨"，用于演示"拒绝" |

这套种子数据让演示可以一气呵成：正常 → 混淆警示 → 拒绝 → 低限额，四种情况全覆盖。

## 4. 代称解析算法

### 4.1 解析流程（`resolvePayee`）

```
输入：代称字符串 "妈玛"，用户 ID
  │
  ① 归一化：NFKC + 去空格 + 繁简转换 + 去标点
  │     "妈玛" → "妈玛"
  │
  ② 精确匹配 aliases：遍历该用户全部联系人
  │     命中 → 单候选 → 直接返回
  │
  ③ 无精确命中 → 模糊匹配（编辑距离 ≤ 1，见 §4.2）
  │     收集全部候选
  │
  ④ 按候选数量分流：
     ├─ 0 个候选 → unknown（拒绝 + 引导）
     ├─ 1 个候选 → 疑似命中，返回 { needConfirm: true, candidate, reason: '名称相近' }
     └─ ≥2 个候选 → 歧义，返回 { ambiguous: true, candidates: [...] }
```

### 4.2 零依赖的中文相似度检测

**难点**：项目零第三方依赖，没有拼音库。

**方案**：编辑距离（Levenshtein）+ 高频同音字表，两者叠加。

```js
// ① 编辑距离：零依赖，20 行，覆盖单字替换/增删
//    "妈妈" vs "妈玛" = 1     ✅ 抓到
//    "小红" vs "小虹" = 1     ✅ 抓到
function levenshtein(a, b) { /* 标准 DP 实现 */ }

// ② 同音字表：覆盖编辑距离抓不到但读音相同的
//    "张" vs "章"（编辑距离 1，但字形无关，读音相同）
//    "妈妈" vs "麻麻"（编辑距离 1）
const HOMOPHONES = {
  '妈': ['馬', '麻', '玛', '蚂'],
  '张': ['章', '彰'],
  '李': ['里', '理'],
  '王': ['汪', '亡'],
  '红': ['虹', '洪', '宏'],
  '小': ['晓', '筱'],
  // ... 30 条左右，覆盖常见姓氏 + 亲属称谓
};
```

**为什么够用**：演示场景不需要覆盖全部汉字。亲属称谓（爸妈爷奶）+ 百家姓前 20 + 常见名字用字，30 条映射表足以覆盖所有可能的演示用例。**这体现的是设计思路，不是覆盖率的完备性。**

### 4.3 歧义处理：绝不自动决策

这是产品体验与安全性的交汇点。三种歧义，三种处理：

**A. 重名（两个"李总"）**

```
🤖 通讯录里有 2 位「李总」，请确认是哪一位：

  ┌────────────────────────────────┐
  │ 李强 · 技术部 · 6222****1234    │ ← 点选
  │ ✅ 已验证 · 转过 8 次           │
  └────────────────────────────────┘
  ┌────────────────────────────────┐
  │ 李明 · 市场部 · 6222****5678    │ ← 点选
  │ ✅ 已验证 · 转过 2 次           │
  └────────────────────────────────┘
```

**B. 谐音相近（"妈玛" → "妈妈"）**

```
🤖 通讯录里没有「妈玛」，但找到一位名称相近的联系人：

  ┌────────────────────────────────┐
  │ ⚠️ 名称相近提醒                 │
  │ 张桂芳 · 6222 **** 1234         │
  │ 代称「妈妈」· ✅ 已验证          │
  │                                 │
  │ 请确认这是你要转账的人吗？       │
  │ [就是 TA]  [不是，换一个人]      │
  └────────────────────────────────┘
```

**关键**：即使只有一个相近候选，也**必须让用户点一次确认**。因为"妈玛"这种谐音正是攻击的典型形态——用户可能真的被社工话术骗了，认为"妈玛"就是妈妈。这一次点击，是最后一道人工防线。

**C. 完全无匹配（"阿姨"）**

```
🤖 通讯录里没有「阿姨」，我无法确定该转给谁。

   为了你的资金安全，我不会猜测收款人。
   [➕ 添加为新联系人]  [📖 从通讯录选择]
```

**体验要点**：拒绝的同时给出两条出路，用户不会卡死。这比冷冰冰的"操作失败"好得多。

## 5. 易混淆标注（确认表单内）

用户决策 2 明确要求：易混淆账号要特殊标注。

**触发条件**：本次解析出的收款人，与通讯录中**其他**联系人的代称/姓名相似度超过阈值。

**展示形态**（确认表单内，红色警示区）：

```
┌─────────────────────────────────────────────┐
│ 🔐 操作确认卡片                    P2 资金   │
├─────────────────────────────────────────────┤
│ 收款人      张桂芳                           │
│ 代称        「妈妈」                         │
│ 账号        6222 **** **** 1234              │

├─────────────────────────────────────────────┤
│ ⚠️ 易混淆提醒                                │
│ 你的通讯录中还有一位「妈玛」（李梅            │
│ 6222****5678），与本次收款人名称高度相似。    │
```

**设计逻辑**：攻击者可以伪造代称，但**伪造不了"你的通讯录里有一个相似的人"这个事实**。这个提醒把隐藏的歧义显式化，让用户在签字前看到。

## 6. 通讯录准入：验证程序（防污染）

用户决策 4 的核心。这是整个方案**最重要的一环**——如果通讯录可以被随意污染，后面所有防护都是空谈。

### 6.1 三种验证方式

| 方式 | 流程 | 证明强度 | 演示可行性 |
|---|---|---|---|
| **短信回填** | 系统向该手机号发验证码 → 要求对方告知验证码 → 用户回填 | 证明手机号归属 | ⭐ 最佳（演示短信面板已有） |
| **小额打款** | 转 ¥0.01 并附 6 位码 → 对方查收后告知 → 用户回填 | 证明**账号**归属 | 真实银行做法，演示稍复杂 |
| **面对面扫码** | 双方在场扫码确认 | 最强 | 演示环境不适用 |

**推荐主推短信回填**：项目已有"演示短信"面板（右下角），验证码本来就公开展示，正好用于演示——**但这恰恰也是要向评委说明的地方**：真实环境验证码只发到对方手机，用户需要向对方索取，这个"索取"动作本身就是一次人工核实。

### 6.2 验证流程（两步）

```
① 用户填写：真实姓名 + 账号 + 手机号 + 代称
      ↓
② 系统发起验证 → 生成 6 位码 → 演示面板展示
      ↓  同时创建 pending 记录（可转 ¥50）
③ 用户从对方处获得验证码并回填
      ↓
④ 校验通过 → trust: 'verified', verifyMethod: 'sms_backfill', verifiedAt: now
      ↓
⑤ 写审计：actor='user', action='contact.verify'
```

### 6.3 三道防污染锁

| 锁 | 机制 |
|---|---|
| **锁 1：验证权归用户** | `verifiedBy` 恒为 `'user'`。Agent 无 `contact.verify` 工具，连调用入口都不存在 |
| **锁 2：Agent 不能添加** | `contact.add` **不注册进 POLICY 白名单**。Agent 调用任何未在策略表的动作，网关直接拦截（已有机制） |
| **锁 3：新联系人风控** | 刚添加（< 24h）的联系人即使已验证，首次转账超过 ¥1000 触发二次确认 + 审计标记 `recentAddedRisk` |

**锁 3 对应的攻击场景**：攻击者社工让用户把骗子加为联系人并完成验证，立刻转走大额。锁 3 无法完全阻止，但**强制了一次额外确认 + 留下审计证据**，把"静默得手"变成"有迹可循且被拦一次"。

## 7. 新账号两步流程（"我妈换卡了"）

用户决策 3：允许，但分两步 + 低限额同步执行。

### 7.1 场景识别

当转账目标账号**不在**该联系人的已验证账号中时，触发新账号流程：

- "我妈刚换卡了，新卡号是 6222...8888，转 5000 给她"
- "妈妈的新账号 6222...8888"

### 7.2 流程

```
① Agent 识别：代称"妈妈"已验证，但账号是新账号
      ↓
② 不覆盖原账号 —— 创建/更新一条 pending 记录：
      { alias: '妈妈的新账号', account: '6222...8888', trust: 'pending' }
      ↓
③ 生成授权单，但金额被限制：
      · 单笔 ≤ ¥50  → 正常生成，红色警示框
      · 单笔 > ¥50  → 拦截，提示"该账号尚未验证"
      ↓
④ 用户如需大额 → 走 §6 验证流程
      ↓
⑤ 验证通过 → 账号并入该联系人，恢复正常限额
```

### 7.3 拦截话术（产品文案）

```
🔶 该收款账号尚未验证

「妈妈」的新账号 6222****8888 还没有完成验证。
为保护你的资金，向未验证账号单笔最多转 ¥50.00。

如需转 ¥5000.00，请先完成验证：
[📲 发送验证短信]  [取消本次转账]

⚠️ 提醒：家人"换卡"是诈骗高发场景。
   建议通过电话或当面与对方核实后再操作。
```

**最后那句提醒是产品层面的加分项**——它不只是拦住，还告诉用户为什么拦、这个场景有什么风险。这体现了产品思考，而不只是技术实现。

## 8. 用户体验精进（五项）

用户明确要求"体验上也有更好的精进"。安全方案最容易犯的错是：越安全越难用。以下是让方案**同时更好用**的设计。

### 精进 1：收款人选择器取代手输（转账页）

**现状**：`<input placeholder="如：小红">` —— 手输、易错、无校验。

**改造后**：

```
┌─ 转账 ──────────────────────────────────┐
│ 🔍 [搜索姓名/代称/账号尾号___________]   │
│                                          │
│ ⭐ 常用                                  │
│  ┌──────────────────────────────────┐   │
│  │ 👤 妈妈 张桂芳                    │   │
│  │    6222****1234  ✅已验证         │   │
│  └──────────────────────────────────┘   │
│  ┌──────────────────────────────────┐   │
│  │ 👤 房东 王强                      │   │
│  │    6222****5678  ✅已验证         │   │
│  └──────────────────────────────────┘   │
│                                          │
│ 🔶 待验证（单笔限 ¥50）                  │
│  ┌──────────────────────────────────┐   │
│  │ 👤 同事小李 李强  [去验证]         │   │
│  │    6222****9012  🔶未验证         │   │
│  └──────────────────────────────────┘   │
│                                          │
│ [➕ 添加新联系人]                        │
└──────────────────────────────────────────┘
```

**体验提升**：点一下就填好，比打字快，且不可能输错。安全感来自"这个人是我亲手加的"，而不是"我打对了字"。

### 精进 2：对话中的收款人确认条（仅在歧义时）

**无歧义**：不插入任何额外步骤，直接生成授权单。

**有歧义**：在生成授权单**之前**插入一个轻量确认条：

```
🤖 找到了，是这位吗？
  ┌───────────────────────────────┐
  │ 👤 张桂芳                      │
  │    代称「妈妈」· 6222****1234  │
  │    ✅ 已验证 · 累计 12 笔       │
  │  [就是 TA]  [换一个人]         │
  └───────────────────────────────┘
```

**为什么放在授权单之前**：如果错了，用户在这一步就能纠正，不用走完"输密码+验证码"才发现人错了。**把纠错成本前置**，这是体验设计的经典手法。

### 精进 3：拒绝时给出出路

见 §4.3C。拒绝 + 引导，而不是拒绝 + 结束。

### 精进 4：把"限制"说成"提额机会"

| 笨说法 | 好说法 |
|---|---|
| "该收款人未验证，转账失败" | "「小李」完成验证后，单笔可提到 ¥50,000 [去验证]" |
| "单笔限额 ¥50" | "未验证账号单笔 ¥50 应急额度，验证后解除" |

同一条规则，后者让用户觉得系统在帮他，而不是在拦他。

### 精进 5：确认表单的身份展示升级

现状只显示 `收款人 小红`。改造后展示全身份（见 §5 的完整表单）。

**这是最关键的一项**——用户决策 2 说的"用户自己可以验证账户或者手机号是否正确无误"，前提是**系统得把账号和手机号显示出来**。当前系统连账号都不显示，用户根本没有核对的可能。

## 9. 技术架构

### 9.1 新增模块 `lib/contacts.js`（约 250 行）

```js
// 收款人可信通讯录：代称解析 + 信任状态判定 + 限额计算
module.exports = {
  // 核心
  resolvePayee(userId, alias),      // → { status, contact, candidates, warning }
  trustLevelOf(userId, account),    // → 'verified' | 'pending' | 'unknown'
  limitFor(trust, userLimits),      // → { single, daily }

  // 准入
  addContact(userId, payload),      // 恒建 pending
  startVerify(userId, contactId),   // 发码
  completeVerify(userId, id, code), // 回填 → verified
  removeContact(userId, contactId),

  // 工具
  normalize(s),                     // NFKC + 去噪
  levenshtein(a, b),                // 编辑距离
  findSimilar(userId, name),        // 易混淆检测
};
```

### 9.2 拦截层新增

在 `lib/gateway.js` 的 `LAYER` 中新增：

```js
const LAYER = {
  DATA:    '数据隔离层',
  RESOLVE: '收款人解析层',   // ← 新增
  POLICY:  '权限层',
  VERIFY:  '校验层'
};
```

**为什么要单列一层**：向评委展示时可以清晰说出"五层拦截，本次攻击被第 N 层拦下"。层次越清晰，说服力越强。

### 9.3 调用位置

```
lib/agent.js  executeIntent()
   │  transfer.execute / scheduled.create
   ▼
【新增】contacts.resolvePayee(user.id, params.toName)
   ├─ unknown  → 返回引导话术（不生成授权单）
   ├─ ambiguous→ 返回候选选择卡（不生成授权单）
   ├─ pending  → 校验金额 ≤ ¥50，超限则拦截
   └─ verified → 继续
   ▼
gateway.createApproval(...)   ← 参数中注入 contactId / toAccount / toPhone
```

### 9.4 授权单参数扩展

```js
params: {
  toName: '张桂芳',        // 改为真实姓名
  toAlias: '妈妈',         // 保留代称供展示
  toAccount: '6222****3445',
  toPhone: '138****1111',
  contactId: 'ct8f3a2c91',
  trust: 'verified',        // 签名涵盖，不可篡改
  amount: '100'
}
```

**注意**：`trust` 字段进入 HMAC 签名范围，攻击者无法通过篡改请求把 `pending` 改成 `verified`。

## 10. API 设计

```
GET    /api/contacts                    列表（含 trust 状态）
POST   /api/contacts                    添加（恒为 pending）
POST   /api/contacts/:id/verify/start   发起验证（发码）
POST   /api/contacts/:id/verify/confirm 回填验证码 → verified
DELETE /api/contacts/:id                删除
POST   /api/contacts/resolve            代称解析（前端实时调用）
```

**权限约束**：以上接口**均不注册进 `POLICY` 白名单**，即 Agent 无法通过 `gateway.agentCall` 调用任何一个。它们在 `server.js` 中直接实现，只校验登录态。

这是"Agent 不能碰通讯录"的技术保证——**不是靠判断，是靠它压根没有调用入口。**

## 13. 分期实施建议

| 期 | 内容 | 价值 | 量 |
|---|---|---|---|
| **一期（核心）** | 数据模型 + 解析层 + 三态限额 + 确认表单身份展示 + 种子数据 | 解决"无法核对身份"的根本问题 | ~400 行 |
| **二期（准入）** | 添加联系人 + 短信回填验证 + 6 个 API | 防通讯录污染 | ~250 行 |
| **三期（体验）** | 收款人选择器、歧义确认条、易混淆检测、引导话术 | 体验精进 | ~250 行 |

**建议一期先落地**——它单独就能把"转账时可以核对账号"这个最大的体验与安全缺口补上，且不影响现有任何演示流程（种子数据里预置"小红"保证旧脚本兼容）。

## 14. 诚实说明：这不能解决什么

即使做完以上全部，仍有两类攻击无法技术根除：

**① 社工型污染**
攻击者通过电话骗用户："我是你妈的朋友，把我加进你的银行通讯录，验证码是 123456。" 用户自己完成了全部验证流程，系统看到的一切都合法。

**能做的**：锁 3（新联系人 24h 内大额二次确认）+ 完整审计。把"静默得手"变成"留痕且被拦一次"，但不能阻止。

**② 用户不核对**
确认表单显示了账号，用户就是不看的。

**能做的**：把关键信息视觉强化（账号加粗、尾号放大、易混淆红标）。提高被注意的概率，但不能保证。

---

**这两条要主动向评委说明。** 声称"完全解决"会显得不专业；说清"防御到哪一层、剩余风险是什么、为什么无法消除"，反而体现工程判断力。

## 15. 答辩话术

> **问：Agent 怎么知道"妈妈"是谁？会不会被骗子利用？**
>
> 三道闸。第一，Agent 只能从用户亲手验证过的通讯录里取人，取不到就停下来问，绝不猜测。第二，即使名字对上了，确认表单会把真实姓名、脱敏账号、手机号、验证时间全部展示出来，用户可以逐项核对；如果通讯录里还有个名字相近的人，系统会红标提醒。第三，向没验证过的账号转账，单笔最多 50 块——这是我特意留的应急通道，但大额必须走验证。
>
> **问：如果骗子骗用户把自己加进通讯录呢？**
>
> 这就是我们必须诚实的地方：技术上拦不住一个"用户自愿验证的骗子"。但三件事做了：第一，验证动作只能用户完成，Agent 连调用入口都没有；第二，新加的联系人 24 小时内大额转账会触发二次确认；第三，全程审计留痕。我们能做到的是让攻击"留痕且被拦一次"，而不是让它静默得手。
>
> **问：为什么不干脆让 Agent 别解析，用户自己选？**
>
> 那就没有接入 Agent 的意义了。我们的原则是"歧义才打断，无歧义不打扰"——通讯录里只有一个妈妈，一步不停直接转账；有两个李总或者名字对不上，才停下来让用户点一下。90% 的正常路径完全无感，安全性靠身份透明和准入验证来保证，不靠增加操作。
